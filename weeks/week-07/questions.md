# Вопросы для самопроверки

1. Зачем нужен файл `.proto`? Почему мы не пишем классы сообщений сразу на Python?
2. Что такое Unary RPC? Чем он концептуально похож на REST запрос?
3. Почему gRPC обычно эффективнее REST (JSON) по процессору и трафику?
4. Что такое "обратная совместимость" в Protobuf и зачем нужны номера полей (тэги, например `= 1`)?
5. Что такое Stub (стаб) на клиенте и Servicer на сервере?
6. В каких случаях вы бы выбрали REST, а в каких — gRPC?


Файл .proto — это единый источник правды для всех языков. Из него генерируются классы под Python, Go, Java и т.д. Если писать классы сразу на Python, то клиент на другом языке не поймёт ваши данные.

Unary RPC — это когда клиент послал один запрос и получил один ответ, как обычный HTTP вызов. Концептуально он похож на REST запрос: «вопрос-ответ».

gRPC эффективнее, потому что Protobuf упаковывает данные в бинарный формат (меньше байт), а JSON — в текстовый. Плюс gRPC использует HTTP/2, а REST часто HTTP/1.1.

Обратная совместимость — когда новую версию протокола понимают старые клиенты. Номера полей (тэги) нужны, чтобы Protobuf знал, какое поле к чему относится, даже если мы переименовали поле или добавили новое.

Stub — это «пульт» на клиенте, через который вызывают удалённые методы. Servicer — это класс на сервере, который содержит реальную логику обработки вызовов.

REST выбирают для простых API, открытых для браузера и мобильных приложений. gRPC выбирают для внутренних сервисов в микросервисной архитектуре, где нужна скорость и строгие контракты.
